Input Telemetry and Actuation Interfaces

How Joulie reads power and facility telemetry, and how the agent sends its control intents. Use it to wire Prometheus, an OpenTelemetry producer or the simulator to Joulie. Exported /metrics are on the Metrics Reference; the CRD fields are on CRD and Policy Model.

Backends

The same control logic runs on real hardware and on simulator or KWOK clusters; environment variables on the agent choose the wiring, never the hardware identity (that is NodeHardware).

HTTP input format

The agent (TELEMETRY_CPU_SOURCE=http) and the controller manager (NODE_POWER_SOURCE=http) read one OTLP JSON ExportMetricsServiceRequest per GET, {node} replaced by the node name. Each component’s power is the rate of its hw.energy counter, or its hw.power gauge while the counter warms up; the agent sums the cpu components, the controller manager cpu and gpu (or hw.host.* with NODE_POWER_SCOPE=host). A body without resourceMetrics is read as the legacy JSON, with a warning. The full rules and a minimal document are on the wiki page Telemetry inputs.

Input metrics (OpenTelemetry)

The controller manager reads node power (NODE_POWER_SOURCE=prometheus, the chart default) and facility readings (ENABLE_FACILITY_METRICS=true) from Prometheus with PromQL instant queries. Producers push them as OpenTelemetry metrics to Prometheus’ OTLP receiver: the simulator in emulate mode, an OpenTelemetry Collector, or any exporter that follows the table below. Only the controller manager queries Prometheus.

Every producer sets the resource attributes k8s.node.name (the node), service.instance.id (unique per producer and node) and service.name. It reports one cpu component per CPU package and one gpu per GPU, whole-host energy only as hw.host.*, and counters that never decrease. Zone and rack names are the nodes’ joulie.io/cooling-zone and joulie.io/rack labels (Node topology).

The queries

Each input is one grouped query per reconcile (node power) or per poll (facility), keyed by node, zone or rack; a node missing from the answer reads source: prometheus-no-data. The otel preset reads the energy rate first and the power gauge only without a counter; kepler and kepler-legacy read Kepler’s node counters. PROMETHEUS_RESOURCE_ATTRIBUTES (auto by default) chooses whether the node label is read from every series or joined from target_info. At start the controller manager logs every query it runs. The full PromQL of each preset, and why it is written that way, is on the wiki page Telemetry inputs.

Prometheus settings

Plain Prometheus, started with --web.enable-otlp-receiver, which serves POST /api/v1/otlp/v1/metrics:

# prometheus.yml
storage:
  tsdb:
    out_of_order_time_window: 30m   # OTLP samples carry the producer's timestamps
otlp:
  promote_resource_attributes: [k8s.node.name, host.name]
  translation_strategy: UnderscoreEscapingWithSuffixes

With the Prometheus Operator, the same through kube-prometheus-stack values (values/prometheus-grafana.yaml sets them; the fields exist in kube-prometheus-stack 91.9.0, prometheus-operator v0.94.1):

prometheus:
  prometheusSpec:
    enableOTLPReceiver: true
    otlp:
      promoteResourceAttributes: [k8s.node.name, host.name]
      translationStrategy: UnderscoreEscapingWithSuffixes
    tsdb:
      outOfOrderTimeWindow: 30m

Install it into the monitoring namespace (helm install telemetry prometheus-community/kube-prometheus-stack -n monitoring --create-namespace -f values/prometheus-grafana.yaml): the chart’s PROMETHEUS_ADDRESS, http://prometheus-operated.monitoring:9090, resolves only there.

Grid carbon intensity

Joulie ships no carbon intensity provider: point FACILITY_CARBON_INTENSITY_QUERY at one you already export, with FACILITY_CARBON_INTENSITY_UNIT and FACILITY_CARBON_INTENSITY_SIGNAL (marginal or average) (Grid carbon intensity). The reading is converted to gCO2eq/kWh, exported as joulie_grid_carbon_intensity_grams_per_kW_h, and handed to the policy, which does not act on it yet.

Diagnostics

The startup log has one input ... line per query. joulie_twin_input_queries_total{input,result} counts each query’s outcome (Twin input metrics), and NodeTwin.status.powerMeasurement.source says whether a node was read.
