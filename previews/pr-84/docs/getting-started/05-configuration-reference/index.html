Configuration Reference

Complete reference for all Joulie environment variables. These are set via Helm values or directly in the Deployment/DaemonSet manifests.

Defaults listed below are the code defaults. The Helm chart (charts/joulie/values.yaml) overrides some of them: notably, the controller manager NODE_SELECTOR defaults to joulie.io/managed=true in the chart even though the code default is node-role.kubernetes.io/worker.

Booleans. The agent, the controller manager and the simulator read every on/off variable the same way: true, 1, yes or on, and false, 0, no or off, in any case, with surrounding spaces ignored. Unset or empty means the default. Any other value keeps the default and logs one warning naming the variable, so a typo never flips a switch. The exceptions are SIM_OTEL_FILE_METRICS, OTEL_SDK_DISABLED and fakesmi’s HWEMU_UNPRIVILEGED, whose rows say how they are read.

Images

The chart values agent.image.tag, controllerManager.image.tag and schedulerExtender.image.tag (and image.tag in the simulator chart) default to empty, which pulls the chart’s appVersion. A chart installed from oci://registry.cern.ch/joulie carries the version it was released with, so it runs the images of that release. A chart installed from a checkout has appVersion: latest and runs the newest stable release. Set a tag only to run other images, for example your own build.

Pre-releases (a GitHub pre-release, or a version such as 0.2.0-rc0) are published under their version only and never move latest.

Every image (joulie-agent, joulie-controller-manager, joulie-scheduler, joulie-simulator) is a multi-arch index of linux/amd64 and linux/arm64, so each node pulls the image of its own architecture. The kubectl plugin is released for linux and darwin, each on amd64 and arm64.

Agent governor control

The agent always discovers the CPU and GPU governors of its node and publishes them in NodeHardware (see Governor discovery). It writes the presets of its NodeTwin, spec.cpu.governor and spec.gpu.governor, only with GOVERNOR_WRITES true; the controller manager writes those fields only with its own GOVERNOR_CONTROL on (see Governor control). The baseline it puts back lives in NodeHardware: it follows every discovery until the agent’s first governor write, so a change an operator makes before writes are on is what a restore puts back, and from that write it stays fixed until a restore. The agent puts it back when a field disappears.

VariableDefaultChartDescription
GOVERNOR_WRITESfalsefalseWrite the governor presets. false reports disabled for a preset and writes no preset. With false the agent still puts back the settings it changed in an earlier run (result restored), once, and writes nothing else.
GOVERNOR_RESTORE_ON_EXITtruetrueOn SIGTERM or SIGINT, put the baseline back before the agent exits, for every component it changed. A rolling update of the agent therefore restores the baseline and the new agent applies the preset again. SIGKILL and OOM kills restore nothing.
  • Writes use the agent’s existing /host-sys mount, root user and privileges, the ones the DVFS fallback uses; the pod spec does not change. Without them the result is refused and NodeHardware shows writable: false.
  • NVIDIA presets run nvidia-smi -i <pci bus id> -lgc or -lmc, so they need nvidia-smi in the agent (see “Agent GPU tools”); without it the result is error, as for caps.
  • In the HTTP control mode (TELEMETRY_CPU_CONTROL or TELEMETRY_GPU_CONTROL http) and in pool mode the agent writes no governor and reports unsupported.
  • What each preset becomes on each CPU driver and GPU family is in CPU support and GPU support.
  • The results, their retries and the restore rules are in Governor control. Check them with:
kubectl get nodetwins -o custom-columns=NODE:.spec.nodeName,CPU-GOV:.status.controlStatus.cpuGovernor.result,CPU-NATIVE:.status.controlStatus.cpuGovernor.applied,GPU-GOV:.status.controlStatus.gpuGovernor.result,GPU-NATIVE:.status.controlStatus.gpuGovernor.applied

Agent GPU tools

The agent reads and caps NVIDIA GPUs by running nvidia-smi from its PATH. AMD GPUs need no tool: the agent reads and writes the power1_cap files of their amdgpu hwmon devices under /host-sys (see Agent host backends), which needs a root agent and a writable /host-sys, as the chart gives by default. It runs rocm-smi --showproductname only as a vendor probe, and never runs amd-smi. Intel GPUs need no tool either: the agent reads and writes the power1_max or power2_max files of their i915 or xe hwmon devices under /host-sys, with the same root agent and writable /host-sys, and reports the GPU control backend host-intel. The agent image (gcr.io/distroless/static) ships no GPU tool, and has no C library and no ELF loader, so mounting the host’s nvidia-smi alone is not enough: it is dynamically linked (file $(command -v nvidia-smi) on a GPU node shows it) and also needs the loader and the NVML library (libnvidia-ml.so.1). The hooks above are where these come in: agent.runtimeClassName for a container runtime that injects the driver’s tools and libraries, such as the NVIDIA one, or agent.extraVolumes and agent.extraVolumeMounts for a host directory, with agent.extraEnv.

The NVIDIA inventory is nvidia-smi --query-gpu=index,power.min_limit,power.max_limit,power.limit,power.draw,name,power.default_limit --format=csv,noheader,nounits; a wrapper that answers for nvidia-smi must answer that query. NodeHardware gpu.capRangePerGpu.defaultWatts is its power.default_limit, and maxWatts when it prints none within the range; on AMD it is always maxWatts, because the driver rewrites power1_cap_default with the cap in force. gpu.powerDomains is the number of GPUs that hold a power limit of their own, published only when it is below gpu.count, as on two-die AMD packages such as the MI250X; the controller manager and the extender multiply the per-GPU maximum by it, and by the count when it is absent.

Which combination works on a real NVIDIA node is an open question: no recipe has been verified yet. After installing, check the GPU control status of every GPU node:

kubectl get nodetwins -o custom-columns=NODE:.spec.nodeName,GPU:.status.controlStatus.gpu.result,MESSAGE:.status.controlStatus.gpu.message

A tool that cannot run shows as error with a message starting gpu inventory failed, or as blocked with no supported GPU backend detected when the vendor cannot be told either; the GPUs then keep their limits. On an AMD node without the amdgpu driver the message is gpu inventory failed: no amdgpu hwmon device under bus/pci/devices, and a cap the driver refuses, or a read-only /host-sys, is error naming the GPU’s bus id. On an Intel node labelled as one without an i915 or xe hwmon device it is gpu inventory failed: no i915 or xe hwmon device with a power limit under bus/pci/devices; Intel GPUs whose driver shows no power<N>_rated_max end blocked with the power limit range of the Intel GPUs is unknown, and a limit the hardware clamps is error with the value it reads back. The simulated cluster reproduces both sides: fakesmi fails as the real tool does when something it needs is missing (HWEMU_ROOTFS under Simulator hardware emulation), and the harness either mounts those files (toolDelivery: mounted) or not (toolDelivery: none).

Managed nodes without an agent

The controller manager plans every managed node, whether or not an agent runs there, and says in the node’s NodeTwin whether one does: the condition AgentReporting in status.conditions, shown in the Agent column of kubectl get nodetwins. It is True (reason NodeHardwareCurrent) while an agent publishes the node’s NodeHardware, and False when no agent has published it (NoNodeHardware) or its last write is more than 15 minutes old (NodeHardwareStale): the caps in spec are then planned and not enforced. The controller manager logs a warning each time a node turns False, and counts the managed nodes per status and reason in the gauge joulie_twin_nodes_agent_reporting (Twin agent coverage). The usual causes are a taint the agent does not tolerate (agent.tolerations), a node outside agent.daemonset.nodeSelector, or an image without the node’s platform.

kubectl get nodetwins -o custom-columns='NODE:.spec.nodeName,AGENT:.status.conditions[?(@.type=="AgentReporting")].status,REASON:.status.conditions[?(@.type=="AgentReporting")].reason'

Measured node power

The controller manager writes each node’s measured power to NodeTwin.status.powerMeasurement.measuredNodePowerW. With NODE_POWER_SOURCE=prometheus, which the chart sets, it runs one grouped PromQL query per reconcile (GET <address>/api/v1/query) and reads every node from the answer; with http it reads one OTLP JSON document per node. The default preset otel reads the OpenTelemetry hardware metrics that producers push to Prometheus’ OTLP receiver: the rate of hw.energy, or the hw.power gauge, of the cpu and gpu components, keyed by the resource attribute k8s.node.name. Input metrics (OpenTelemetry) has the contract, every preset query and the Prometheus settings it needs.

The Chart column is what charts/joulie/values.yaml sets; “unset” means the code default applies.

They are read only when the new name is unset, and the controller manager logs a warning naming the replacement.

A custom query must return instantaneous power in watts. Energy exporters publish cumulative joules counters, which grow without bound, so they have to be converted with rate(); the presets already do:

rate(kepler_node_platform_joules_total{exported_instance="{node}"}[5m])

NODE_POWER_PRESET=kepler-legacy with NODE_POWER_SCOPE=host reads the same series without a custom query. Passing a counter directly makes measuredNodePowerW climb forever, which drives power headroom negative and cooling stress to 100% on every node. The controller manager logs a warning when a reading exceeds twice the node’s TDP.

Upgrading from v0.2: see Upgrading.

Governor control

Off by default. With GOVERNOR_CONTROL on, the controller manager writes a vendor-neutral governor preset into each managed node’s NodeTwin (spec.cpu.governor, spec.gpu.governor), chosen by the profile the node runs at; the agent maps it to the node’s native settings. Nothing changes on a node until its agent also runs with GOVERNOR_WRITES true. Which node gets which preset: Governor policy.

CPU_GOVERNOR_ECO_PRESETefficiencyCPU preset of eco nodes. Provisional: in the simulator’s governor exploration it saved 0.5 % energy for a 22.2 % eco p95 slowdown, above the experiment’s 20 % limit.

GPU_GOVERNOR_MODEL_PRESETS_JSON{}Presets per GPU model: {"<model>": {"performance": "<preset>", "eco": "<preset>", "ecoCeilingPctOfMax": <pct>}}. A field left out keeps the default above, "" writes none for that model, and an invalid field is dropped with a warning.
GPU_GOVERNOR_SUSTAINED_ONLY_MULTI_GPUfalseIf true, a node whose GPU preset is sustained gets it only while a running pod on it requests 2 or more GPUs (units of any GPU resource: whole GPUs, MIG devices, partitions, shared replicas), and no GPU governor otherwise.

GPU presets: auto is the vendor default. sustained holds the data-path clocks (memory, fabric) at their maximum and keeps idle gating, leaving the compute clock free to idle; a demand-driven governor sees only a GPU’s own kernels, so a GPU that receives a peer transfer can stay at low data-path clocks, and on families where those clocks bound the transfer, sustained removes that limit at some idle power. No default selects it: opt a model in through GPU_GOVERNOR_MODEL_PRESETS_JSON once a measurement on that model shows the gain. efficient puts the compute clock under the ceiling and leaves the data path dynamic. low and peak are for experiments; peak turns idle gating off on AMD GPUs. These defaults are provisional until measured. Hardware modeling says what each preset means, and Governor policy which node gets which.

The overview dashboard’s “Agent: Governors” row plots the presets in effect (joulie_agent_governor_state) and the writes per result (joulie_agent_governor_writes_total).

Facility metrics

The facility poller reads six inputs from Prometheus, each with one grouped query per poll. The outdoor ambient temperature, IT power and cooling power are one value each; the twin uses the IT power for PSU stress and the ambient temperature for cooling stress, and the controller manager logs PUE as (IT power + cooling power) / IT power. The zone, rack and node inputs return one series per cooling zone, rack or node (see “Node topology” below). An input whose query fails or returns nothing is unknown until a later poll reads it, never the value of an earlier poll. Every query is counted in joulie_twin_input_queries_total{input,result}, and the three single values are exported as joulie_twin_facility_* (Metrics).

Node topology

Joulie supports optional per-rack PSU stress and per-zone cooling stress. This is activated by adding standard node labels:

  • joulie.io/rack: physical rack identifier (e.g., rack-1)
  • joulie.io/cooling-zone: cooling zone identifier (e.g., zone-a)

When these labels are present, the controller manager computes PSU stress per rack instead of cluster-wide: the rack’s power is the facility’s rack power input (FACILITY_RACK_POWER_QUERY, keyed by the joulie.io/rack value) when it reads that rack, otherwise the sum of the estimated power of the rack’s nodes. The ambient temperature of a node’s twin is the most local one known: the node’s inlet temperature (FACILITY_NODE_INLET_TEMP_QUERY), then its cooling zone’s (FACILITY_ZONE_AMBIENT_TEMP_QUERY, keyed by the joulie.io/cooling-zone value), then the outdoor ambient. The twin model interfaces remain the same; topology just groups nodes for more accurate stress computation.

Nodes without topology labels fall back to cluster-wide stress computation, and still use their inlet temperature when the facility reads one.

The simulator (simulator/cmd/simulator) reads these variables at startup to build its base hardware profile. A node class in SIM_NODE_CLASS_CONFIG overrides one per node with the key in parentheses, under the class’s model:.

Simulator physics step

The simulator (simulator/cmd/simulator) advances the model of a node outside the emulate-mode cluster spec only in a physics step, in simulated time; a read or a control never advances it. A step splits its time into equal substeps, and the energy it books is the integral of the instantaneous power over them. See Power Simulator.

Simulator telemetry export

In emulate mode the simulator (simulator/cmd/simulator) pushes OpenTelemetry metrics of every emulated node and of the facility as OTLP JSON over HTTP, for example straight to a Prometheus started with --web.enable-otlp-receiver. Events are always written to events.jsonl and pushed only when a logs endpoint is set. Names and Prometheus spellings: Simulator Metrics.

In every mode the simulator also answers reads of one node over HTTP: GET /otlp/telemetry/{node} and GET /telemetry/{node} serve the same OTLP JSON ExportMetricsServiceRequest, the format TELEMETRY_CPU_HTTP_ENDPOINT and NODE_POWER_HTTP_ENDPOINT read. ?format=legacy serves the deprecated packagePowerWatts JSON until v0.4.0, with one warning per process. ?format=otlp asks for the default explicitly; any other format value is refused with 400.

VariableDefaultDescription
SIM_EXPORTERS(empty)Comma-separated compatibility exporters to serve at /exporters/<name>/metrics: kepler-0.7, kepler-0.12, dcgm-4.8.4, amd-dme-1.5.2 (ROCm device-metrics-exporter v1.5.2, AMD GPUs). kepler-0.12 reads the RAPL zones of each node’s tree, and serves its GPU series only with SIM_KEPLER012_GPU. An unknown name stops the start and lists the valid ones. See Compatibility exporters.

The export follows the OpenTelemetry exporter specification with three deviations:

  • Only http/json is supported; the specification’s default is http/protobuf, and any other protocol stops the start.
  • Nothing is pushed without an endpoint; the specification’s default is http://localhost:4318.
  • A 404 from the logs endpoint turns the logs push off after one warning. Prometheus has no logs receiver, so a base endpoint pointing at Prometheus would otherwise fail on every push.

Points are cumulative: Prometheus rejects delta temporality unless its otlp-deltatocumulative feature is on. A push is retried on 429, 502, 503 and 504, honouring Retry-After, and never on 400 (such as out-of-order samples) or 500. Each request carries at most 64 node resources, plus the facility. A per-signal endpoint is used exactly as given, so it needs the full path; a base URL there is a common mistake.

Simulator hardware profiles

The simulator (simulator/cmd/simulator) emulates a node from a hardware profile picked by name: one of the builtin profiles in simulator/pkg/hwemu/profiles/, or a local one. Local profiles stay outside the repository and are the only ones whose measured sources (measured: provenance) may name the machine they were measured on, such as a calibration of your own nodes. A builtin profile may cite a measurement too, but describes the machine by its hardware only.

VariableDefaultDescription
SIM_PROFILES_DIR(empty)Directory of local hardware profiles: every *.yaml file directly in it, each with a name equal to its file name without .yaml. Empty means the builtin profiles only, and so does a directory with no *.yaml in it, such as a mounted ConfigMap that holds no profile yet. Hidden entries (a leading dot) are skipped. A directory that does not exist, a path that is not a directory and a *.yml file, or a .yaml suffix in another case such as .YAML, are errors, never a fallback to the builtins.

A local profile may extend (extends:) a builtin profile or another local one, by the same merge rules the builtins use. It may not take a builtin’s name, since one of the two would be hidden: give it a new name and extend the builtin instead. The simulator logs the local profiles once, as local profiles loaded dir=<dir> profiles=<names>.

kubectl plugin

The kubectl joulie plugin requires no configuration. It reads your current kubeconfig context.

# Install
go build -o kubectl-joulie ./cmd/kubectl-joulie
mv kubectl-joulie /usr/local/bin/

# Usage
kubectl joulie status      # cluster energy overview
