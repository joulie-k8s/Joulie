Hardware Modeling and Physical Power Model

This page says what Joulie models about CPUs and GPUs and where the numbers come from. The agent uses these facts to resolve caps; the simulator uses them to turn utilization and controls into power and slowdown.

In the simulator these models are a test bed for Joulie’s behaviour, not evidence of energy savings: they rest on vendor figures, public measurements and assumptions. What meaningful experiments need is tracked in the milestone Evidence-based evaluation.

Validation status. Some catalog CPUs run public measured curves. GPU support is validated in simulation only. For GPUs and the other CPUs, the model combines official documentation with literature-based priors until direct calibration is possible.

Data provenance

Every modelled value has one of three kinds of provenance; a proxy is never presented as a measurement.

KindExamples
Official or read at runtimeCPU base and boost clocks, TDP and cTDP; GPU board power; cap ranges the node reports; CPU frequency landmarks and GPU clock ranges, which the agent publishes in NodeHardware (status.cpu.landmarks, status.gpu.governor.clockRangesMHz) as facts, not telemetry

Proxy or inferredEPYC 9534 (from the 9654), EPYC 9375F (from the 9655), Xeon Gold 6530 (from an Intel family proxy); the simulator borrows no curve from a proxy, so these nodes run the analytic model

Hardware inventory

The catalog (pkg/hwinv/assets/hardware.yaml, read through pkg/hwinv/catalog.go) holds CPU and GPU entries, and a node is a discovered CPU model and count plus a GPU model and count. The agent, the controller manager and the simulator all read the same embedded copy, unless HARDWARE_CATALOG_PATH (SIM_HARDWARE_CATALOG_PATH for the simulator) replaces it. Model names are matched by alias after normalization.

Hardware not in the catalog

Unknown hardware degrades realism; it does not break the control loop.

  • The CPU and the GPU fall back independently to the generic model, or to no throttling.
  • The simulator fills four facts in a fixed order: the node class key, else the environment variable, else the catalog, else a built-in constant (the variables are in the configuration reference).
  • An unknown GPU is capped between 80 and 300 W unless a class or a variable says otherwise.
  • On a real node the agent still uses the cap limits the node reports.

CPU model

A CPU with a public SPECpower curve (2x EPYC 9654, 9655 and 9965) runs that curve; any other runs an analytic model, idle + (max - idle) x util^alpha x f^beta, with a peak of sockets x TDP for a catalog CPU. A cap lowers the frequency until the package meets it, settling as a first-order lag. Compute-bound work slows with the frequency; memory-bound work slows little until the frequency falls below a knee. Telemetry is averaged, and thermal throttling is opt-in. The equations, defaults and sources are on CPU power model.

GPU model

Each physical GPU is modelled on its own, and a node’s GPU cap is the same per-device cap on every GPU. A workload has a natural power draw, lower for memory-bound work; a cap only matters once it falls below that draw. Under the cap, compute-bound work slows as ratio^computeGamma, fitted per family to published throughput (H100 SXM 0.43, H100 NVL 0.50, MI300X 0.62, L40S 1.20, others 1.0); memory-bound work slows less. Caps settle over a lag of 150 ms (350 ms on MI300X), and exported power is averaged over 1 s, as NVML reports it on NVIDIA, except on MI300X, whose driver reports instantaneous power. The equations, per-family values and sources are on GPU power model.

Workload boundness

Each job carries cpuUtilization, gpuUtilization, memoryIntensity, ioIntensity and cpuFeedIntensityGpu, rather than a single label. Memory and IO intensity soften the slowdown a CPU cap or DVFS causes. A GPU job with a high CPU feed intensity also slows when the CPU is throttled.

Heterogeneous caps

The controller manager writes caps as percentages by default (CPU of its cap range, GPU of the per-device maximum), and the agent or the simulator resolves them into watts from the node’s own hardware data. Absolute per-device caps remain possible for deterministic experiments.

What the simulator exports

Node CPU and GPU power (averaged and instantaneous), per-GPU caps, power and temperature, thermal-throttle fractions, performance multipliers, integrated energy and job completion statistics. See Power Simulator.

6.8 Emulated nodes: governor and clock physics

An emulated node (emulate mode) runs the CPU and GPU governors its profile describes; the other modes keep an implied performance governor.

  • CPU. Each cpufreq policy’s governor sets a frequency every 100 ms substep, following the Linux v6.12 rules (phys.GovernorStep); powersave under intel_pstate with HWP and amd-pstate-epp follows an assumed EPP-shaped curve. Slower clocks keep the CPU busy longer for the same work, and a binding RAPL or HSMP cap wins over every governor.
  • GPU. The cap and the governor are two limits on one clock: the GPU runs at the lower of the two, never at their product (phys.GPUPowerWithClock, phys.GPUThroughputWithClock).
  • Parameters. Every value is assumed and to be calibrated.

The rules per governor are on Governors; the GPU clock rules and parameters on GPU power model.

Preset names

The emulator names the preset a CPU package or a GPU runs (the joulie.hw.governor.preset attribute of its metrics) with the reverse mapping of pkg/governor (ReverseCPU, ReverseAMD, ReverseNvidia): the name is the preset whose plan the agent would write for that state. A state that no preset, or more than one, maps to has no name, and a GPU without a mapping table reports none. The tie-breaking rules are on Governors.

Peer transfers

GPU to GPU copies share each receiver’s gpus.transfer.peerLinkGBps. A family can have a receiver gate (gpus.transfer.receiverGate): a receiver whose data path is at its lowest level, or idle under auto, lets through only a fraction of the link. The gate is off in every builtin profile; SIM_GPU_RECEIVER_GATE=on turns it on for what-if runs. Details are on GPU power model.

6.9 Governor presets

A frequency governor is a control dimension of its own, next to the power cap: the cap bounds the power, the governor chooses the frequency below that bound. Joulie writes one vendor-neutral preset per component in NodeTwin.spec, and pkg/governor is the only place a preset becomes a native setting. The mapping is per driver in CPU support and per GPU family in GPU support.

  • Restored. The agent records the state it found before its first write and restores it when a preset disappears, when writes are turned off, and on exit (Governor control).
