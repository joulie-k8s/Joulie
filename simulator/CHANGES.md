# Simulator changes

This file lists every change since Joulie v0.2.3 that moves the numbers the simulator produces for its modelled nodes (standalone mode, and Kubernetes mode without emulation), and how far each one moved them. A result produced with an older simulator holds for the model it ran; read it together with this table. Emulated nodes (`SIM_EMULATE`) run the physics of `simulator/pkg/hwemu` and are not covered here.

The reports of experiments 01 to 03 in [`experiments/`](../experiments) were produced before every change below; each carries a dated note that says which of its model statements did not hold, followed by a rerun of its benchmark with the 0.2.4 release images (2026-10-24, one seed).

## Two yardsticks

**The reference scenario** lives in `simulator/cmd/simulator/testdata/reference/`: eight inventory entries (nine nodes), one for each way the simulator resolves a node's model (a SPECpower curve, the same CPU on one socket, a second curve, a proxy CPU, an Intel CPU with official figures only, catalog GPUs on an Intel and on an EPYC host, GPUs the catalog does not know), and 40 jobs over 2 h. It runs in standalone mode under baselines A, B and C with `SIM_SA_WORKERS=1`, `SIM_SA_DT=5`, `SIM_SA_TIMEOUT=7200`, the code defaults and the embedded catalog. Its test, `go test ./simulator/cmd/simulator/ -run ReferenceScenario`, compares the run with `reference.golden.json` (energy as `hw.energy` by `hw.type` and by node, job statistics as `joulie.sim.*`) and fails on any key that moves by more than a relative 1e-9, printing a table of what moved.

**The debug runs** are each experiment's `configs/benchmark-debug.yaml` through the standalone sweep: one seed, 800 jobs (01) or 600 (02 and 03), 300 s of simulated time, all three baselines.

```bash
PATH=$HOME/.local/go/bin:$PATH python3 scripts/standalone_sweep.py \
  --config experiments/02-heterogeneous-benchmark/configs/benchmark-debug.yaml \
  --simulator <simulator binary> --results-dir <directory>
```

Energy in the tables is the integral of the power a run reports: the sum over the rows of `timeseries.csv` of `cpu_power_w + gpu_power_w`, times the 5 s step. From the stepNode change on it equals the golden's `hw.energy` total to within 0.001 %. The saving of B or C is 1 minus its energy over A's. Every simulator binary ran the same trace of each experiment.

**How each change was measured.** From the stepNode change on, each one compares the tree just before it with the tree just after it. The earlier changes were measured on the v0.2.3 simulator, with the old and the new behaviour selected through its inputs: the thermal thresholds through `SIM_{CPU,GPU}_THERMAL_THROTTLE_{START,FULL}_C`, the catalog corrections and the generated catalog through `SIM_HARDWARE_CATALOG_PATH`. With all of them selected, v0.2.3 gives the same energy as the tree just before the stepNode change: identical on the reference scenario, and within 0.03 % on the debug runs, less than two identical runs of that simulator differ on GPU nodes (up to 0.05 %). The other changes in between (the curve cap solver among them, and the emulate mode, workload and OpenTelemetry work) therefore moved neither yardstick.

## Changes

| Change | What changed | Reference scenario | Debug runs |
|---|---|---|---|
| Thermal throttling is opt-in | `SIM_{CPU,GPU}_THERMAL_THROTTLE_{START,FULL}_C` default to 0, which means off; they were 85 and 97 °C for CPUs, 82 and 92 °C for GPUs. A 2x EPYC 9654 node at full load on its SPECpower curve headed for 126 °C, throttled fully at 97 °C, dropped to 141 W with throughput 0, cooled and swung back. | A +0.2 %, B and C +1.1 %; B and C complete 30 jobs instead of 29 | under 0.02 %, within the run-to-run spread |
| A curve node throttles under its cap | Above its RAPL cap, a node on a measured curve now lowers its frequency on its own curve (`phys.SolveFreqScaleForCap`). Before, the curve clamped its power to the cap, so the solver never saw the excess and the node kept full frequency and full throughput. This change leaves the analytic model's power unchanged; its cap solver changed later, see the row on memory traffic. | none: standalone eco sets a CPU frequency scale and the default CPU cap is 5000 W, so no CPU cap binds | none, for the same reason |
| Catalog corrections | `AMD_EPYC_9655` `node2S` is SPEC result 01457, 126 to 751 W (was 138 to 861 W); `minBoardPowerW` of `NVIDIA_H100_SXM` is 300 W (was 350) and of `AMD_INSTINCT_MI300X` 400 W (was 350). | A -1.3 %, B and C -1.7 %, all on the EPYC 9655 node | none at the time: the experiments read a generated catalog |
| The experiments read the embedded catalog | The sweep and the installers no longer generate a catalog from the inventory (it gave every CPU a 300 W TDP and no curve, so every CPU ran the analytic model at 80 W idle and 420 W peak) and clear `SIM_HARDWARE_CATALOG_PATH`. | none: it always read the embedded catalog | A +108 % (01), +12 % (02), +19 % (03); the saving of C falls from 31.2 to 17.0 % (01), 31.8 to 30.4 % (02), 34.5 to 33.6 % (03) |
| stepNode | The physics of a modelled node advances only in `stepNode`, in simulated time and in substeps (`SIM_SA_SUBSTEP` in standalone mode, 100 ms on the physics tick `SIM_PHYSICS_TICK` otherwise); HTTP reads and gauges no longer advance it, and energy is the integral of the instantaneous power. | power unchanged; the reported energy (`energy_cumulative_j`) now equals its integral, where it ran 2.5 to 3.1 % below it and changed between identical runs | power: B and C -0.1 % in 02 and 03, as the GPU cap lag now runs in simulated time; the reported energy now equals the integral of the power, where it ran 18 to 51 % below it and changed between identical runs |
| Artifact removals | Removed: the cut of idle CPU power on a node with a throttle target (up to 50 % below 20 % utilization), so idle power no longer depends on whether Joulie manages the node; the deep idle state of a capped idle GPU (10 % of idle power), so a board never draws less than its idle power; and the report of cap plus headroom for a cap below the power at the lowest frequency, so such a node reports what it draws there. | A unchanged, B and C +0.2 % (the curve nodes) | A unchanged; B +0.6, +3.1, +4.5 % and C +0.9, +4.6, +6.4 % (01, 02, 03); the saving of C falls from 17.0 to 16.3 % (01), 30.4 to 27.2 % (02), 33.6 to 29.4 % (03) |
| A GPU cap slows a job once | A GPU cap slows a GPU job by what the capped board model says it costs. The legacy progress formula charged it a second time, by the cap over the board maximum weighted by the job's GPU sensitivity. | none | none: no job with a GPU sensitivity ran on a capped GPU |
| Catalog facts reach the model | With no environment or class value, a node takes from the catalog its GPU maximum and lowest cap per board (they were 300 and 80 W unless an environment variable or a class set them), its CPU socket cap range (TDP down to the lowest cTDP, else 0.55 x TDP) and, without a curve, a peak of sockets x TDP (was 420 W); `node2S` curves scale with the socket count. `SIM_POD_W`, `SIM_DVFS_DROP_W_PER_PCT`, `SIM_GPU_ALPHA_UTIL` and `SIM_GPU_BETA_CAP` are removed and warn once. | A +61 %, B and C +63 %: GPU energy x2.07; CPU energy of A -5 %, mostly the one-socket node, whose curve now halves | A +4.2 % (01), +32 % (02), +20 % (03); the saving of C rises from 16.3 to 17.3 % (01), 27.2 to 30.5 % (02), 29.4 to 32.6 % (03) |
| Standalone runs hwemu profiles | An inventory entry may name an hwemu `profile`; legacy entries honour `gpu_min_cap_watts` and `gpu_max_cap_watts`; eco on a profile node with a writable PL1 is a CPU power cap. | none | none: no profile nodes, and the inventories' GPU cap ranges equal the catalog's |
| The analytic cap solver counts memory traffic | `phys.SolveFreqScaleForCap` on the analytic model now inverts the power formula with the memory and IO activity factor that the power it then computes applies. Before, a capped node with memory or IO intensity above 0 drew below its cap (262.5 W under a 300 W cap). 20 of the 548 cases in `testdata/physics/analytic-cpu-power.golden.json` moved, all capped with memory or IO traffic; no saturation flag changed. | none: no CPU cap binds in the reference scenario | not rerun |
| An unknown GPU takes its labelled count | A node whose GPU the catalog does not know takes its device count from the `joulie.io/hw.gpu-count` label (the inventory's `gpu_count` in standalone mode). Before, it got 0 GPUs and drew no GPU power. | `ref-gpu-unknown` now draws power for its 4 GPUs: its energy in baseline A rose from about 1.09 MJ to 8.44 MJ; only the GPU and `ref-gpu-unknown` energy keys moved, in A, B and C | not rerun |
| Cap ranges stay ordered | An explicit `SIM_CPU_SOCKET_CAP_MIN_W` or `SIM_GPU_MIN_CAP_WATTS_PER_GPU` above the maximum the catalog fills in is lowered to that maximum, with a warning. Before, the range came out inverted (200 to 165 W on a Xeon Platinum 8260). | none: the reference scenario sets no explicit minimum | none, for the same reason |
| Clock suffix in CPU names | Catalog matching drops a trailing clock token and the `cpu` before it, so the label-safe form of a full cpuinfo name such as `Intel(R) Xeon(R) Platinum 8260 CPU @ 2.40GHz` matches its catalog entry instead of falling back to the generic model. | none: the reference inventory spells its models without the suffix | not rerun |
| Eco GPU nodes keep their CPU uncapped | The controller manager wrote `spec.cpu.packagePowerCapWatts` at `ECO_CAP_WATTS` (120 W by default) on eco GPU nodes, and the agent applied it, although a GPU node is meant to get GPU caps only; the CPU of a GPU node now gets `PERFORMANCE_CAP_WATTS` whatever the profile, as on a performance GPU node. Only Kubernetes mode, where the controller manager drives the agents, moves: CPU power and job speed on eco GPU nodes. Standalone mode does not run the controller manager and still scales the CPU frequency of eco GPU nodes, so the two modes differ there until it follows. | none: standalone mode | none, standalone mode; Kubernetes mode not rerun |
| Governor and clock physics in emulate mode | An emulated node whose profile has the governor facts, every builtin profile, runs its cpufreq governor as the kernel does (`phys.GovernorStep`: schedutil, ondemand, conservative, userspace, and the EPP-driven powersave of intel_pstate with HWP and amd-pstate-epp), counts work in cycles, so a governor that holds a lower frequency shows the same work as a busier CPU in power and utilization, and measures CPU job speed against performance at `cpuinfo_max_freq` with the profile's boost instead of against the governor's own frequency, which made a governor cost nothing by construction. GPU clock locks, levels and overdrive ceilings, forced data-path levels and idle gating off reach GPU power and speed (`phys.GPUPowerWithClock`, `phys.GPUThroughputWithClock`), and peer transfers are counted per GPU. What moved, in emulate mode only: CPU power and job speed under every governor but performance, for example a fully loaded 2x Xeon 8260 under its shipped powersave with EPP balance_performance runs at 3.32 of 3.9 GHz, 140.6 W per package instead of 165 W, and a `cpu.compute_bound` job at 0.87 of the reference speed instead of 1; an AMD GPU under `auto` draws `dataPathHoldW` (10 W, assumed) more while its data path holds after its own memory-active work. Unchanged: every node under performance, every GPU without a lock or a forced level, and every profile without the governor facts. | none: standalone mode does not run hwemu nodes | none, for the same reason |
| Standalone eco GPU nodes keep their CPU at full frequency | Standalone mode now follows the controller manager (the row above): the CPU of an eco GPU node runs as on a performance node, at frequency scale 1 under the performance cap, and only its GPUs take the eco cap. Before, standalone scaled the CPU frequency of an eco GPU node to `SIM_SA_CPU_ECO_PCT` (60 % by default and in the debug runs), or capped its PL1 at that share of the maximum on a profile with a writable PL1. | none: each GPU family of the reference scenario has one node, and every family keeps one performance node | 01 none (no GPU node); energy of B +0.59 % and C +0.66 % (02), B +0.42 % and C +0.63 % (03), all of it CPU energy of eco GPU nodes; the saving of B falls from 21.4 to 21.0 % (02) and 22.5 to 22.1 % (03), of C from 30.5 to 30.0 % (02) and 32.6 to 32.2 % (03) |
| GPU clock model: a lower cap or clock never raises power or throughput | The cap and the governor are two limits on one clock (`phys.GPUPowerWithClock`, `phys.GPUThroughputWithClock`). The GPU runs at the lower of the governor's clock and the cap-implied clock, (cap / natural)^ComputeGamma; its compute share is that clock, its memory share the lower of the capped board's memory scale and the memory knee at the governor's clock, and its power the capped board power, its dynamic part scaled by (clock / cap-implied clock)^ClockBeta below the cap-implied clock, but never more than the governor's clock draws without a cap, idle + (P_natural - idle) x r^ClockBeta. With ComputeGamma x ClockBeta x (1 - IdleW / MaxW) <= 1 that bound never binds and the power is as before: a lock at the cap-implied clock draws the cap, and a lock above it changes nothing. Beyond it, a lock at or above the cap-implied clock draws the lower of the cap and its uncapped power, at the cap's compute share. Before, the memory share of a locked GPU was relative to the knee at the cap-implied clock, so below the knee a lower cap raised it (the throughput of a memory-bound GPU locked at 0.3 of its maximum clock rose from 0.32 to 0.55 as the cap came down, test parameters), and beyond the bound a cap raised a locked GPU's power above its uncapped power (202 W under a cap against 134 W without one). At the maximum clock both still equal the capped board model. | none: the clock model runs on emulated nodes only | none, for the same reason |
| The efficient GPU preset defaults to 80 % | `governor.DefaultCeilingPctOfMax`, the compute clock ceiling of `efficient` when neither the NodeTwin nor `GPU_GOVERNOR_ECO_CEILING_PCT_OF_MAX` names one, is 80 % of the maximum compute clock (was 75 %). In the Tier A sweep of the [governor exploration](../website/content/en/docs/experiments/governor-exploration.md), eco GPU work at 75 % had a p95 slowdown of +22.5 % for -13.2 % energy, above the 20 % the eco class allows, and at 80 % +17.3 % for -10.7 %. The value is provisional: the saving rests on the assumed `clockBeta` and `memoryKneeFrac`, which a clock sweep on each GPU family must measure. What moves: eco GPU nodes under governor control (`GOVERNOR_CONTROL` gpu or all, off by default), which in the simulator only emulated nodes model. | none: standalone mode writes no governor | none, for the same reason |
| The 2x EPYC 9654 profiles run their SPECpower curve | `amd-epyc-2s-energy-only` and `amd-instinct-mi300x-8gpu`, which extends it, run `physics.cpu.model: catalog-curve`: the curve of the catalog's `AMD_EPYC_9654` entry (SPECpower_ssj2008 result 01203), split over the two packages, in place of the analytic model of their `idlePkgW` and `maxPkgW`, which the 9534 and HSMP profiles keep. Package power of a 2x EPYC 9654 node, analytic then curve: idle 80 and 128 W under schedutil and performance; at 10 % load 117.8 and 271.2 W under schedutil, 125.3 and 257 W under performance; at 50 % load 368.4 and 410.0 W under schedutil; at full load 720 and 817 W. Under performance, 10 % load adds 7.1 % of the dynamic range with the analytic model and 18.7 % on the curve. What moves: emulated nodes and standalone profile nodes of these two profiles, which experiment 05's configs and the governor presets example use. | none: the reference scenario names no profile | none: no debug run names a profile |

No change moved the number of completed jobs of the debug runs.

## Adding a change

A change that moves a number of a modelled node (physics in `nodephys.go`, model resolution in `modelresolve.go`, job speed, the catalog, the standalone policy) adds a row here in the same pull request:

1. Run `go test ./simulator/cmd/simulator/ -run ReferenceScenario` on the change; the failure prints the keys that moved. Review them, then rewrite the golden with `-update` and commit it.
2. Build the simulator before and after the change and run the three debug configurations with each binary on the same traces: the sweep reuses the trace it finds in `<results-dir>/traces/`, so copy that directory from the first run into the second run's results directory.
3. Add the row: what changed, and the reference and debug-run deltas. A change that moves neither yardstick but changes another mode (Kubernetes mode caps, emulate mode) still gets a row that says so.
4. Add a dated note to the reports of any experiment whose description the change makes untrue.
