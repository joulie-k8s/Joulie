# Simulator changes

This file lists every change since Joulie v0.2.3 that moves the numbers the simulator produces for its modelled nodes (standalone mode, and Kubernetes mode without emulation), and how far each one moved them. A result produced with an older simulator holds for the model it ran; read it together with this table. Emulated nodes (`SIM_EMULATE`) run the physics of `simulator/pkg/hwemu` and are not covered here.

The reports of experiments 01 to 03 in [`experiments/`](../experiments) were produced before every change below; each carries a dated note that says which of its model statements did not hold, followed by a rerun of its benchmark with the 0.2.4 release images (2026-10-24, one seed).

## Two yardsticks

**The reference scenario** lives in `simulator/cmd/simulator/testdata/reference/`: eight inventory entries (nine nodes), one for each way the simulator resolves a node's model (a SPECpower curve, the same CPU on one socket, a second curve, a proxy CPU, an Intel CPU with official figures only, catalog GPUs on an Intel and on an EPYC host, GPUs the catalog does not know), and 40 jobs over 2 h. It runs in standalone mode under baselines A, B and C with `SIM_SA_WORKERS=1`, `SIM_SA_DT=5`, `SIM_SA_TIMEOUT=7200`, the code defaults and the embedded catalog. Its test, `go test ./simulator/cmd/simulator/ -run ReferenceScenario`, compares the run with `reference.golden.json` (energy as `hw.energy` by `hw.type` and by node, job statistics as `joulie.sim.*`) and fails on any key that moves by more than a relative 1e-9, printing a table of what moved.

**The debug runs** are each experiment's `configs/benchmark-debug.yaml` through the standalone sweep: one seed, 800 jobs (01) or 600 (02 and 03), 300 s of simulated time, all three baselines.

```bash
PATH=$HOME/.local/go/bin:$PATH python3 scripts/standalone_sweep.py \
  --config experiments/02-heterogeneous-benchmark/configs/benchmark-debug.yaml \
  --simulator <simulator binary> --results-dir <directory>
```

Energy in the tables is the integral of the power a run reports: the sum over the rows of `timeseries.csv` of `cpu_power_w + gpu_power_w`, times the 5 s step. From the stepNode change on it equals the golden's `hw.energy` total to within 0.001 %. The saving of B or C is 1 minus its energy over A's. Every simulator binary ran the same trace of each experiment.

**How each change was measured.** From the stepNode change on, each one compares the tree just before it with the tree just after it. The earlier changes were measured on the v0.2.3 simulator, with the old and the new behaviour selected through its inputs: the thermal thresholds through `SIM_{CPU,GPU}_THERMAL_THROTTLE_{START,FULL}_C`, the catalog corrections and the generated catalog through `SIM_HARDWARE_CATALOG_PATH`. With all of them selected, v0.2.3 gives the same energy as the tree just before the stepNode change: identical on the reference scenario, and within 0.03 % on the debug runs, less than two identical runs of that simulator differ on GPU nodes (up to 0.05 %). The other changes in between (the curve cap solver among them, and the emulate mode, workload and OpenTelemetry work) therefore moved neither yardstick.

| GPU clock model: a lower cap or clock never raises power or throughput | The cap and the governor are two limits on one clock (`phys.GPUPowerWithClock`, `phys.GPUThroughputWithClock`). The GPU runs at the lower of the governor's clock and the cap-implied clock, (cap / natural)^ComputeGamma; its compute share is that clock, its memory share the lower of the capped board's memory scale and the memory knee at the governor's clock, and its power the capped board power, its dynamic part scaled by (clock / cap-implied clock)^ClockBeta below the cap-implied clock, but never more than the governor's clock draws without a cap, idle + (P_natural - idle) x r^ClockBeta. With ComputeGamma x ClockBeta x (1 - IdleW / MaxW) <= 1 that bound never binds and the power is as before: a lock at the cap-implied clock draws the cap, and a lock above it changes nothing. Beyond it, a lock at or above the cap-implied clock draws the lower of the cap and its uncapped power, at the cap's compute share. Before, the memory share of a locked GPU was relative to the knee at the cap-implied clock, so below the knee a lower cap raised it (the throughput of a memory-bound GPU locked at 0.3 of its maximum clock rose from 0.32 to 0.55 as the cap came down, test parameters), and beyond the bound a cap raised a locked GPU's power above its uncapped power (202 W under a cap against 134 W without one). At the maximum clock both still equal the capped board model. | none: the clock model runs on emulated nodes only | none, for the same reason |

## Adding a change

A change that moves a number of a modelled node (physics in `nodephys.go`, model resolution in `modelresolve.go`, job speed, the catalog, the standalone policy) adds a row here in the same pull request:

1. Run `go test ./simulator/cmd/simulator/ -run ReferenceScenario` on the change; the failure prints the keys that moved. Review them, then rewrite the golden with `-update` and commit it.
2. Build the simulator before and after the change and run the three debug configurations with each binary on the same traces: the sweep reuses the trace it finds in `<results-dir>/traces/`, so copy that directory from the first run into the second run's results directory.
3. Add the row: what changed, and the reference and debug-run deltas. A change that moves neither yardstick but changes another mode (Kubernetes mode caps, emulate mode) still gets a row that says so.
4. Add a dated note to the reports of any experiment whose description the change makes untrue.
